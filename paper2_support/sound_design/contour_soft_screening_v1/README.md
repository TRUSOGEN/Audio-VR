# Contour-Soft Screening Candidates

This folder contains four controlled candidate families for a pre-screening comparison. It does not contain final study stimuli.

| Candidate | Single change from current contour | Purpose |
| --- | --- | --- |
| C0 | No change | Reference |
| C1 | Remove only T03's 1040 Hz late tick | Test the late-tick hypothesis |
| C2 | Reduce only the second-harmonic weight from 0.26 to 0.10 | Test whether a softer harmonic balance improves comfort |
| C3 | Change only the envelope exponent from 0.85 to 1.65 | Test a slower onset and offset |

The parameter values are engineering screening values. They are not prescribed by the warning-sound literature and they are not a final decision about frequency, duration, level, or timbre.

All files are deterministic mono 44.1 kHz PCM16 WAV, 1.35 s, target digital RMS 0.15, and peak no greater than 0.75. These digital controls do not establish ear-side loudness, SNR, audibility, comfort, or perceived urgency.

## Reproduce and audit

```sh
python3 generate_contour_soft_candidates.py
python3 audit_contour_soft_candidates.py
```

The audit writes `candidate_analysis.json` with checksum, format, duration, digital peak, and digital RMS for each WAV.

## Remaining human gate

Researcher audition, HMD/headphone calibration, formative screening, visual-task HMD dry run, and feasibility pilot remain required before one family can be selected for the study.

This is a **researcher QA** check for one non-speech candidate in quiet, without a route, map, GO/WAIT activity or speech condition. It is not a replacement for the four-condition main study or an approved participant-data collection tool. No personal identifiers are requested and no records are uploaded.

- Select C0–C3 and provisional trial count/window; defaults 18 and 8 s are convenience settings, not frozen protocol values.
- All three WAVs are checked against `candidate_analysis.json` SHA-256 before training. Each mapping example must finish once; further replay is allowed and logged. This is familiarisation, not a learning pass criterion.
- Each test target is sampled independently and uniformly with replacement using browser crypto randomness. Repeats are allowed; no three-item quota or no-repeat rule creates a predictable final item. Finite runs need not be balanced and may omit a target; they must not be accepted as adequate screening merely because the program ends.
- The testing view shows no target name, file path, progress target, correctness or next target. Answer buttons keep fixed positions. This is presentation masking, not tamper-resistant or experimenter blinding.
- First response within the software window is accepted; timeouts retain null RT. Early/duplicate/late inputs are not accepted. A sound finishes before the next playback, even after an early answer. Tab hiding or audio-context interruption ends an active check as technical interruption.
- Download/copy the JSON after completion or stopping. It contains the full sequence, asset hashes, familiarisation exposures, responses and software times. RT is not measured acoustic onset; browser/headphone latency and actual audibility remain unverified.
- Browser QA records generated by an agent are software evidence only. Before involving participants, define ethics coverage, playback chain, learning criterion, trial coverage and interpretation rules in the existing screening protocol.

The pure state logic is in `identification_core.mjs`; the DOM/audio integration is in `identification_app.mjs`. Relevant boundary tests and the agent-operated browser record are in `../../temp/identification_validity_20260922/`.
