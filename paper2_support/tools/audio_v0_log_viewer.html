Researcher guide

Evidence labels, local files, review snapshots and pilot data

Before a human session: the current Assets/AudioV0.unity scene is serialized as formalStudyMode=false, storageCategory=technical_demo, with an operator ID and candidate settings. It is not pilot-ready. Confirm ethics, consent, approved protocol, approved data location, calibrated audio and the frozen Unity profile before collecting pilot data. Do not relabel or move a technical log into another category.

What Evidence category means

  • technical_demo: software and operator checks; never participant results.
  • pilot: approved feasibility sessions; supports process decisions, not condition-effect claims.
  • participant_run: frozen and approved main-study collection; still requires validation.

The category is a provenance label, not a quality score or proof of human participation. Synthetic or operator markers can make a recording QA-only. The viewer label does not replace export validation.

Where the session files are

On this Mac, Unity writes each session to ~/AudioV0_Data/<storage_category>/<session_id>/. For a pilot, that is ~/AudioV0_Data/pilot/. Unity creates event_log.jsonl (raw events) and session_manifest.json (session metadata). After the session folder appears, create run_record.json beside them, before the first block, using the exact folder ID and approved frozen configuration. Keep the JSONL unchanged; do not put names, contact details or consent forms in this tree. This local path is not yet an approved long-term archive.

How to use this viewer

  1. Choose the category and session. Filter by condition, block or route as needed.
  2. Use Condition comparison for accuracy, correct response time, confidence and GO/WAIT; use Flight recording for trajectory and vertical position. Event audit shows raw event rows for the selected scope.
  3. Each plot's Cleaned CSV contains derived rows used for that metric; Excluded CSV lists rows and reasons left out. Missing values stay blank, and wrong answers remain in accuracy. Image and CSV downloads use the same review snapshot.
  4. The plots are snapshots, not live charts. Click Reload local recordings to include events written since the last load. Reload after a server restart or snapshot-expiry error.

What to do with pilot data

Use a feasibility pilot (planned 2–3 people) to record whether the procedure, route pacing and comfort, cue audibility, task difficulty, left/right controls, learning and logging work. Do not use it to test condition effects, select a winning sound, or claim sound-only identification: the current route presents T01/T02/T03 in order, so scenery and phase order can support guesses.

  1. Preserve the raw session folder. Record the pseudonym, run ID, validation status, observations and deviations in docs/feasibility_pilot_record.md.
  2. Run tools/export_audio_v0_events.py without --allow-technical, using the exact session ID and a new empty derived-output folder at the approved location. Check validation_report.json and sessions.csv; a valid export is not an inferential analysis.
  3. Compare observations with the predefined feasibility exit checks and document whether to hold, iterate or freeze. A change to task, audio, route, timing or controls needs a new version and another affected dry run. Freeze the analysis plan and sample-size/precision rationale before the main study.

The approved long-term raw archive and derived-output locations are still to be decided. Formal analysis must follow the approved protocol and data plan, not this descriptive viewer alone.
